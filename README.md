## Память агента без вектор-БД

Идея простая: долговременная память агента - это не отдельная база и не сервис поверх модели, а **обычная папка с md-файлами** плюс два правила в конфиге проекта.

1. **Один всегда подгружаемый индекс** - `MEMORY.md`. Одна строка на память: заголовок, ссылка на файл, короткий крючок «о чём это». Индекс попадает в контекст на старте каждой сессии.
2. **Каждый факт - отдельный файл** с YAML-frontmatter. Агент дописывает новый файл, когда узнаёт что-то, что должно пережить сессию, и добавляет строку-указатель в индекс.

Всё. «Включение» такой памяти - это буквально протокол в `CLAUDE.md` / `AGENTS.md` проекта (см. [`CLAUDE.example.md`](./CLAUDE.example.md)), никакой механики поверх модели нет.

### Почему не RAG / вектор-БД

Индекс, который целиком помещается в контекст, снимает сам этап retrieval: модель видит оглавление и открывает нужный файл, как человек открывает доки по содержанию. Вектор остаётся для другого класса задач - больших слабоструктурированных текстов, где нет ни оглавления, ни жёсткого синтаксиса. Подробный разбор - в [статье на Хабре](https://habr.com/ru/articles/1071530/).

### Формат файла памяти

```markdown
---
name: <имя этого файла без .md - в точности, буква в букву>
description: <одна строка про то, ЧЕМ является файл - стабильный крючок, не журнал фактов>
metadata:
  type: user | feedback | project | reference
---

<сам факт. Связанные памяти линкуем через [[их-name]].>
```

Типы:

- `user` - кто пользователь (роль, экспертиза, предпочтения);
- `feedback` - как нам работать (правила и корректировки; с «почему»);
- `project` - идущая работа, цели, ограничения, не выводимые из кода;
- `reference` - указатели на внешние ресурсы (URL, дашборды, тикеты).

`description` держите стабильным однострочным крючком: новые факты идут в **тело** файла, а не в `description` (иначе он разрастётся и перестанет работать как короткий сигнал релевантности). `[[links]]` - мягкие ссылки, по которым ходит агент (вне Obsidian не кликабельны). `metadata.type` - соглашение для навигации, тулинг его не парсит.

Примеры - в [`memory/`](./memory).

### Индекс (`MEMORY.md`)

```markdown
- [Профиль пользователя](user_example.md) - senior backend, TypeScript
- [Стиль коммитов](feedback_example.md) - Conventional Commits, без эмодзи
- [Проект: demo-api](project_example.md) - учебный REST на Fastify
- [Дашборды](reference_example.md) - Grafana + статус-страница
```

**Форма адреса одна - голый путь.** `(<файл.md>)` и `(файл.md "подсказка")` - законный markdown, но проверка их отвергает, называя правильную форму. Угловые скобки в markdown нужны ровно для пробела в пути, а после правила про имена (L6) пробелов там не бывает; подсказка в кавычках в индексе бессмысленна - описание несёт крючок после дефиса, а читает индекс агент, которому наводить нечем. На **внешние** адреса правило не распространяется: `(<https://example.com>)` и `(https://example.com "подсказка")` - обычный markdown, и проверка сначала выясняет, наш ли это адрес, и только потом придирается к записи.

**Форма строки одна.** Markdown знает ещё две. Форму через метку (`- [Текст][prof]` плюс `[prof]: файл.md`) проверка отвергает с явной ошибкой, называя, во что переписать. Сокращённая (`- [prof]`) строкой индекса не считается вовсе - это проза, и вот почему так лучше. Это сознательное сужение: формат индекса у́же, чем markdown, и проверка требует формат, а не валидный markdown. Отвергает громко намеренно - если просто не разбирать чужую форму, строки не станут строками, файлы всплывут сиротами, и человек будет видеть свои строки глазами, не понимая претензии.

Следствие приятное: `- [ ]`, `- [x]` и любое `[слово]` в списке - обычная проза. Пока сокращённая форма считалась строкой индекса, чеклисты приходилось отличать отдельным правилом, и на этом уже ломались.

Индекс подключается в `CLAUDE.md` строкой импорта `@memory/MEMORY.md` (Claude Code подтягивает его содержимое в контекст каждую сессию), поэтому он всегда загружен. Остальные файлы модель открывает по крючку из строки индекса.

### Рост

Когда индекс разрастается, его бьют на под-индексы по темам (или каталогам), а корневой `MEMORY.md` держат тонким оглавлением оглавлений. Принцип тот же: всегда-в-контексте только навигация, содержимое - по требованию.

### Проверка согласованности

Плата за простоту - ручная аккуратность: индекс и файлы держит в согласии человек. Часть расхождений ловится машинно, для них есть [`scripts/check_memory_index.py`](./scripts/check_memory_index.py):

| | Что проверяет | Итог |
|---|---|---|
| **L1** | каждая ссылка из индекса ведёт на существующий файл | ошибка |
| **L2** | каждый файл памяти достижим от **корневого** индекса | ошибка |
| **L3** | нет двух разных файлов с одинаковым заголовком и нет буквально повторённой строки индекса | предупреждение |
| **L4** | ссылка `[[имя]]` из тела факта ведёт к существующей памяти | предупреждение |
| **L5** | поле `name` в шапке равно имени файла | ошибка |
| **L6** | имена файлов и каталогов памяти - слаги | ошибка |

L2 - именно достижимость, а не «упомянут где-нибудь»: до под-индекса, на который никто не ссылается, агент не дойдёт, а значит не дойдёт и до перечисленных в нём файлов. Подробнее - ниже. Файл, до которого от корневого индекса не дойти, дальше называется **сиротой** - тем же словом названы ключ `--allow-orphan` и пометка `orphan: true`, а вывод проверки говорит про такой файл «не упомянут ни в одном индексе». Это одно и то же.

**Каждая находка называет действие, а не только диагноз.** Вывод рассчитан на то, что его можно передать агенту как задание: в строке есть адрес (файл и номер строки), что именно не сходится и что с этим делать - вплоть до готовой строки, которую надо вписать в индекс. Там, где написание выдаёт опечатку однозначно, проверка называет и файл, который имелся в виду.

**Имена в памяти - слаги:** строчная латиница, цифры, дефис и подчёркивание, первый символ буква или цифра (L6). Правило одинаково для файлов и для подпапок - каталог входит в адрес наравне с именем файла, и `- [Сервер](Моя Папка/prod.md)` это тот же пробел, только этажом выше. Имя индекса задаётся отдельно и под правило не попадает.

Это тоже сужение формата, и оно снимает сразу три беды. **Пробел**: ссылка `[[имя]]` отличается от прозы в двойных скобках («`[[владелец проекта]]`») только тем, что в имени пробела не бывает - иначе пришлось бы выбирать между враньём на прозе и молчанием о части ссылок. **Процент и решётка**: `%20` в markdown-адресе это escape-последовательность, и файл `план%20дел.md` давал две ошибки на здоровой памяти. **Регистр**: `User.md` и `user.md` на Windows один файл, а на Linux два, и память, зелёная у автора, краснела в CI.

Замер, прежде чем вводить: 391 файл-факт в восьми живых памятях портфеля, **ни одного нарушения**. Правило описывает то, как уже пишут. Цена - кириллица в именах файлов памяти запрещена, хотя она законна и в git, и в файловой системе.

**У памяти одно имя - имя её файла.** Поле `name` в шапке объявляет то же самое, а не второе имя, и расхождение - ошибка (L5). Пока принимались оба написания, ссылка `[[…]]` могла вести то по одному, то по другому, и промахнуться мимо обоих было легче, чем попасть: в восьми памятях портфеля поле расходится с именем файла у 238 файлов из 391. Правило дешевле обработчика.

L4 смотрит связи **между фактами** - ту самую форму `[[их-name]]`, которой формат велит их связывать. Это предупреждение, а не ошибка: проверка обычно приезжает в память, где такие связи уже накопились, и блокировать первый же коммит значит научить человека жать `--no-verify`.

**Найденное не прячется нигде, в том числе при коммите.** Предупреждения печатаются и под ключом `--quiet`, которым проверку зовёт хук; ключ гасит ровно одну вещь - строку «Память согласована» на здоровой памяти. Список битых связей выводится целиком, без обрезки: чинят по адресу, а не по числу. Коммит при этом не блокируется - предупреждение остаётся предупреждением.

```bash
python scripts/check_memory_index.py memory
```

Скрипт только читает файлы, ничего не изменяет, зависимостей не требует. Нужен **Python 3.9 или новее**; в CI гоняются 3.9 и 3.13, на Linux и на Windows ([`.github/workflows/memory-check.yml`](./.github/workflows/memory-check.yml)).

Подразумевается, что папка памяти лежит **в репозитории под git**: так она и задумана - версионируется, ревьюится, едет с проектом. Папки облачной синхронизации как место для памяти не рассматриваются. Коды возврата: `0` - порядок, `1` - нарушения, `2` - проверку выполнить не удалось (это не то же самое, что нарушение).

Направлять проверку нужно на **папку памяти**, а не на корень репозитория: если корневого индекса в самой папке нет, а нашёлся он где-то во вложенных каталогах, она откажется работать с кодом 2 - скорее всего вы указали не ту папку. Но если в папке лежат **файлы памяти** (шапка с `name` или `description`), а корневого индекса нет, - это уже нарушение, код 1: агент не увидит ни одного из них, и это худшее, что может случиться с такой памятью. Внутри папки памяти проверяются файлы `.md`; всё прочее (`.txt`, картинки, вложения) памятью не считается и в индексе не требуется. Не заходит проверка в два вида каталогов: **скрытых** (на точку - это `.obsidian`, `.trash` и прочее хозяйство редакторов, а не факты) и **связанных** (симлинки и виндовые junction'ы - это чужая память, за неё проверка не отвечает). Ссылку внутрь связанного каталога она при этом разрешит, если файл открывается системой. Про каждый пропущенный связанный каталог печатается строка: по выводу должно быть видно, где проверка не была, иначе «сюда не заходили» не отличить от «проверено и чисто».

**Одна память за прогон.** Если у вас рядом лежит несколько памятей - скажем, по папке на агента, - направляйте проверку на каждую отдельно. Общего корневого индекса у такого дерева нет и быть не должно: «корневой индекс ровно один» - свойство одной памяти, а не каталога, в котором их семь. На родительскую папку проверка ответит кодом 1 и скажет прямо: «вы указали папку, внутри которой лежит НЕСКОЛЬКО памятей, проверяйте каждую отдельно». Код 1, а не 2, потому что файлы памяти в такой папке есть - а корневого индекса, который бы их собрал, нет.

**Код 2 - это «проверить не удалось», и он честнее нуля.** Его возвращают отсутствие папки, указанная не та папка и любой разбор, выполненный наполовину: незакрытый блок кода или html-комментарий в индексе (строки ниже в разбор не попали), нечитаемый индекс, нечитаемый файл памяти (по нему не проверены ни связи, ни поле `name`), каталог, который не открылся. Сказать про такую память «согласована» нельзя - о забытых в индексе файлах судить не из чего. Хук на коде 2 коммит **не блокирует**: это не нарушение, а сообщение, что проверка не отработала.

Важная оговорка: код 2 приходит, **только если нарушений не нашлось**. Недоразобранный индекс обычно рождает сирот - и тогда вернётся 1, коммит будет заблокирован, а заметка про незакрытый забор напечатается рядом как объяснение. То есть «незакрытый блок кода → код 2» верно лишь тогда, когда, кроме него, придраться не к чему. В CI - наоборот: шаг `run:` проваливает джобу на любом ненулевом коде и двойку от единицы не отличает. Это сделано намеренно (мягко на коммите, жёстко на входе в основную ветку), но знать про расхождение стоит: локально прошло молча, а галочка красная.

**Корневой индекс один.** Это файл с именем `MEMORY.md`, лежащий в самой папке памяти - тот, что загружается в контекст. Под-индекс - файл с **тем же именем** в подпапке: `memory/MEMORY.md` корневой, `memory/infra/MEMORY.md` под-индекс. Двух корневых так не бывает по построению, и проверке не приходится гадать, какой из лежащих рядом файлов загрузится. Другое имя задаётся ключом `--index` - именно **имя**, не шаблон: `--index INDEX.md`.

Под-индекс, до которого от корневого нет цепочки ссылок, считается ошибкой: к нему неоткуда прийти, значит невидим и он, и всё, что за ним. Достижимость проверяется транзитивно, а не на один шаг.

Файл, названный иначе - `spisok-infra.md` или `MEMORY_infra.md` в корне, - для проверки обычный файл памяти: его строки не разбираются, битые ссылки внутри него не ловятся, а то, на что он ссылается, всплывает сиротами. Если такой файл лежит в корне и похож на индекс по имени и содержимому, проверка скажет об этом отдельной строкой - иначе стена сирот читается как её собственная поломка.

### Проверка того, что тесты не врут

Зелёный набор говорит «ошибок не нашли», а не «ошибки не пройдут». Разница видна, только если сломать код нарочно и посмотреть, заметит ли кто-нибудь:

```bash
python scripts/mutation_check.py
```

Скрипт по очереди портит значимые ветки и после каждой порчи гоняет весь набор. Выжившая мутация - ветка, которую можно молча сломать, и конкретный адрес, куда дописать проверку. Инструмент правит файлы в рабочем дереве и возвращает обратно, поэтому запускать его стоит на чистом дереве; если прогон оборвётся, следующий запуск восстановит файл сам. Это кухня сопровождающего: правило простое - поменяли ветку, поправьте её мутацию в том же файле. Ненайденный якорь и мутант, который не компилируется, - жёсткая ошибка, а не пропуск.

### Подключение хука

**Чтобы проверка шла на каждый коммит** - подключите хук. Сначала посмотрите, не занято ли место:

```bash
git config --get core.hooksPath
```

**Пусто** (команда ничего не напечатала и вернула ненулевой код - это нормально) - значит своих хуков у вас нет, подключайте напрямую:

```bash
git config core.hooksPath .githooks
```

**Что-то напечатано** - у вас уже стоит husky (`.husky/_`), lefthook или другой менеджер хуков. **Не перезаписывайте.** `core.hooksPath` не добавляет папку, а **заменяет** её: чужие хуки перестанут работать молча, без ошибки. И `ln -s` в `.git/hooks` тут не спасёт - при заданном `core.hooksPath` git в эту папку вообще не смотрит. Правильный способ - вызвать наш хук **из вашего**, одной строкой:

```sh
sh "$(git rev-parse --show-toplevel)/.githooks/pre-commit" || exit 1
```

Эта строка - для **husky**: `.husky/pre-commit` это обычный shell-скрипт, и строка ложится в него как есть.

Для **lefthook** голая строка не годится - `lefthook.yml` разберёт её как значение, а не как команду. Там нужен свой вид:

```yaml
pre-commit:
  commands:
    memory-check:
      run: sh "$(git rev-parse --show-toplevel)/.githooks/pre-commit"
```

Учтите: подключение хука - **локальная настройка клона**. `.git/config` не коммитится, поэтому каждый включает его у себя сам, и на свежем клоне это нужно повторить.

Дополнительные ключи проверки хук берёт из настройки репозитория:

```bash
git config memorycheck.args "--allow-orphan templates/*.md"
```

Значение делится по пробелам и **оболочкой не разбирается**: кавычки внутри него не работают, шаблоны не раскрываются (это намеренно - иначе `templates/*.md` подменился бы на файлы из корня вашего репозитория), а аргумент с пробелом внутри задать нельзя.

Убедиться, что хук работает, стоит сразу - и **настоящей попыткой коммита**, а не запуском файла. Запуск `sh .githooks/pre-commit` проверяет только скрипт: он ничего не скажет ни про то, подключён ли хук вообще, ни про потерянный бит исполнения, ни про `CRLF`.

Проверка целиком (команды - в Git Bash):

```bash
printf 'proverka\n' > memory/proverka-huka.md   # файла нет в индексе - это нарушение
git add memory/proverka-huka.md
git commit -m "проверка хука"                   # ДОЛЖЕН быть отклонён
git rm -f --cached memory/proverka-huka.md && rm memory/proverka-huka.md
```

Ваш `MEMORY.md` при этом не трогается вовсе, и после уборки `git status` снова чист. Проверка одинакова при любом способе подключения: и с `core.hooksPath`, и с husky, и с lefthook важно ровно одно - что коммит отклонён.

Коммит прошёл - значит хук не подключён либо не запускается, и вы не защищены: откатите его `git reset HEAD~1` и вернитесь к настройке. `git commit --dry-run` для проверки не годится - хуки он не запускает.

Разовый обход - `git commit --no-verify`.

#### Как отключить хук совсем

Команда зависит от того, чем он подключён, и вслепую тут советовать нечего. Сначала посмотрите:

```bash
git config --show-origin --get core.hooksPath
```

- напечатало `.githooks` - уберите ключ там, где он задан (файл конфигурации виден в выводе `--show-origin`);
- напечатало что-то другое (`.husky/_` и подобное) - у вас свой менеджер хуков, и наш хук зовётся строкой из него; убирать надо её;
- не напечатало ничего - ключ не задан вовсе, так работают lefthook и обычный `.git/hooks/pre-commit`; уберите вызов там, где вписали (`lefthook.yml` или сам файл хука).

**Ключ `core.hooksPath` вслепую не снимайте.** У человека с husky в нём лежит `.husky/_`, и снятие уберёт не наш хук, а весь его набор - молча, без ошибки. А если ключ задан глобально, правка тронет локальный конфиг и не изменит ничего. Поэтому сначала `--show-origin`, и убирайте ровно то, что вписывали сами.

**Дерево против коммита.** Git кладёт в коммит только то, что вы добавили; проверка ходит по папке на диске. Это две разные кучи файлов, и знать про расхождение стоит - оно проявляется в обе стороны.

Одну сторону хук закрывает сам: **неотслеживаемые файлы памяти он из проверки исключает**. Недописанный черновик в `memory/` - нормальное рабочее состояние, а не ошибка, и блокировать из-за него совершенно здоровый коммит значит приучать к `--no-verify`. Исключение узкое: только то, что в репозиторий не поедет **вовсе**. Отслеживаемые файлы - в том числе с несохранёнными правками и удалённые - проверяются как обычно, и стоит сделать `git add` черновика, как он тут же перестаёт быть исключением и строка в индексе с него потребуется.

У исключения две границы, и обе хук называет вслух. Если неотслеживаемых файлов в памяти больше двухсот, он не исключает их по одному - командная строка не резиновая, а на Windows она короче всего, - и проверка идёт по всей папке. И если имя файла требует кавычек (управляющие символы, кавычка, обратный слэш), такой файл не исключается: разбирать это в `sh` - отдельная задача, и честнее заблокировать коммит, чем молча просочиться.

Вторая сторона остаётся: если вы дописали строку в `MEMORY.md`, а **сам файл добавить в коммит забыли**, хук пропустит - на диске файл есть, ссылка выглядит живой. В репозиторий уедет строка без файла, и увидит это уже CI на pull request. Хук - первая линия, а не единственная.

**Строка импорта.** Хук отдельно смотрит, есть ли в конфиге агента строка `@memory/MEMORY.md` — та единственная, из-за которой индекс вообще попадает в контекст. Без неё агент не увидит **ни одного** факта: папка на месте, всё внутри согласовано, а он про неё не знает. Ищется она в `CLAUDE.md`, `AGENTS.md` и в тех же файлах внутри `.claude/`; имя индекса берётся то же, что у проверки (с учётом `--index`).

Это **предупреждение, а не блокировка**, и намеренно: `grep` подтверждает, что строка написана, но не то, что она сработала. Настоящая проверка прежняя — открыть новую сессию и спросить агента, что он знает из памяти. Если конфига агента нет вовсе, хук молчит: судить не по чему.

Сама проверка согласованности в это не лезет — она отвечает строго за папку памяти и наружу не выходит. Конфиг лежит этажом выше, поэтому смотрит туда хук, который и так работает с репозиторием целиком.

Что хук делает и чего не делает: смотрит только папку `memory/` в корне репозитория, запускается лишь когда файлы памяти попали в коммит, и проверяет **рабочее дерево**, а не в точности то, что вы коммитите. Во время `rebase` проверка пропускается - там дерево в промежуточном состоянии, а обойти её нечем, - и хук об этом говорит вслух. Конфликтный `merge`, `cherry-pick` и `revert` не пропускаются - склейка конфликта как раз и ломает строки индекса. Обойти проверку там можно, но по-разному: у `merge` есть свой `--no-verify`, а у `cherry-pick` и `revert` его нет - им нужен обычный `git commit --no-verify`, который завершает текущий шаг, а остальные шаги диапазона продолжает `git cherry-pick --continue` (или `git revert --continue`). Хук подсказывает это прямо в сообщении. `--quit` не используйте: он бросает очередь молча, и оставшиеся коммиты диапазона просто пропадают. Если подходящего Питона в системе нет, проверка пропускается - вслух, но без блокировки вашей работы.

### Исключения из проверки

**Если файл лежит вне индекса намеренно** (шаблон, черновик, заготовка) - скажите об этом явно, иначе L2 будет ругаться вечно:

```markdown
---
name: shablon
orphan: true
---
```

**Способ ровно один, и он в шапке.** `orphan: true` учитывается только внутри `---`, и другого написания нет: файл, который просто рассказывает про эту метку, себя не освобождает - в примере кода шапки не бывает. Нет шапки - нет и способа пометить файл. Шапка предполагается у каждого файла памяти, рядом с `name` и `description`, но её НАЛИЧИЕ проверка не требует: правило запрещает расхождение имён, а не молчание. Ключи формата читаются только с нулевым отступом - `metadata.orphan: true` внутри вложенной структуры это чужое поле, а не метка.

**Метка снимает вопрос только с самого файла.** Если пометить ею под-индекс, до которого от корневого нет цепочки ссылок, достижимее он не станет: файлы, перечисленные в нём, по-прежнему невидимы агенту и всплывут сиротами - проверка скажет об этом отдельной строкой.

**Чтобы исключить целую ветку**, помечать по одному файлу не нужно (а для чужих или сгенерированных каталогов и невозможно) - есть ключ:

```bash
python scripts/check_memory_index.py memory --allow-orphan "templates/*.md"
```

Шаблоны в нём сравниваются с учётом регистра, одинаково на всех системах. Для хука тот же ключ передаётся настройкой `memorycheck.args` - это не отдельный механизм, а единственный способ доставить ключ туда, где проверку зовёт хук, а не вы. В настройке ключ пишется **без кавычек**: её значение оболочкой не разбирается, и кавычки попадут внутрь шаблона.

Ключ значит «сюда проверка не смотрит»: путь под шаблоном не проверяется ни на упоминание в индексе (L2), ни на имя (L6), ни на поле `name` (L5), ни на связи `[[…]]` внутри него (L4). Иначе обещание было бы невыполнимым: у чужого или сгенерированного каталога имя почти наверняка не слаг, переименовать чужое нельзя, а битые связи в чужом файле чинить нечем - и хук показывал бы их на каждом коммите.

Одно исключение, и оно осмысленное: **L1 продолжает действовать**. Ссылка из индекса, ведущая внутрь исключённого пути, обязана разрешаться - строка в индексе написана вами, и адрес в ней либо верен, либо нет.

Итого способов не ругаться на файл вне индекса — два: метка в шапке для одного файла и `--allow-orphan` для группы. И поправка, которую делает **хук**, а не само правило: он передаёт неотслеживаемые файлы этим же ключом, поэтому черновик в `memory/` коммит не блокирует. При ручном запуске проверки тот же черновик числится сиротой - она ходит по диску и про git не знает ничего.

**Чего проверка не делает.** Внешние адреса (`https://...`) она не трогает: это отдельная задача, ей нужны сеть, повторы и кэш, и для неё есть готовые инструменты вроде [lychee](https://github.com/lycheeverse/lychee). И главное - она не ловит **смысловые** дубли, когда два файла про одно понятие названы по-разному. L3 видит только совпадение заголовка слово в слово. Индекс намеренно не уникальный ключ: на стыке общего и частного модель открывает оба файла и сводит их, поэтому структурный дубль машина отсечёт, а близкие по смыслу заголовки развести не сможет - это остаётся на ревью.

Ещё пять границ, которые лучше знать заранее, чем выяснять на своей памяти.

- **`[[имя с пробелом]]` не проверяется**, как и `[[a]]` короче двух символов, и `[[имя|подпись со [скобками]]]`. L4 считает ссылкой только слаг без пробелов и длиной от двух знаков, а квадратные скобки внутри двойных обрывают разбор: связь пишется `[[имя]]`, подпись со скобками - уже не наш формат. Иначе проза в двойных скобках («`[[владелец проекта]]`») сыпала бы предупреждениями на ровном месте, а ложная тревога дороже пропуска: она приучает жать `--no-verify`. Цена - ссылки в стиле Obsidian по умолчанию проходят мимо. Ложных находок это не даёт, только пропуски.
- **Ссылки между РАЗНЫМИ папками памяти L4 не разрешает.** Проверка смотрит одну папку за прогон, и факт, ссылающийся на факт из соседней памяти, для неё битый. В нашем портфеле так набирается 14 предупреждений из 98 - шумовой фон, который не почините.
- **`sparse-checkout` даёт ложные L1**: часть файлов физически отсутствует, и проверка честно говорит, что ссылка ведёт в никуда. Проверяйте на полном чекауте.
- **Литеральная `#` в имени файла** ломает разбор адреса: решётка отделяет якорь, и `a#b.md` читается как «файл `a`, якорь `b`». Три ошибки на ровном месте. Процент безопасен - разворачивание `%20` убрано вместе с формами, которым оно было нужно, - но и он, и решётка запрещены правилом имени (L6), так что до разбора адреса дело обычно не доходит.
- **Имена устройств DOS** (`con.md`, `nul.md`) на Windows диагностируются неверно - как «ссылка выходит за папку памяти»: система разрешает такой путь в устройство, а не в файл. Прописные `CON.md` под правило имени и так не проходят, опасно именно строчное написание - законный слаг. Файл законен на Linux и приезжает в клон на Windows; случай узкий, но если он ваш - переименуйте.

И тонкость про регистр: после правила имени (L6) прописная буква в имени - блокирующая ошибка на любой системе, поэтому пара `User.md` / `user.md` в проходящей проверку памяти невозможна по построению. Остаётся узкий случай существующей памяти, которую ещё не привели к правилу: на Windows такие два файла - один файл, и выбирать не из чего; на Linux их два, и в подсказке про регистр проверка возьмёт первый по алфавиту.

### Тесты и CI

Тесты самой проверки - [`scripts/test_check_memory_index.py`](./scripts/test_check_memory_index.py):

```bash
python -m unittest discover -s scripts -p 'test_*.py'
```

Если гоняете этот набор **в своём проекте**, один тест поведёт себя иначе: проверка того, что хук лежит в индексе git исполняемым, вне git-репозитория пропускается вслух, а в git-репозитории, где хук ещё не добавлен, - падает и говорит, какие две команды выполнить. Это не поломка набора, это тот самый чеклист копирования.

Тесты хука требуют `sh`. Если его не нашлось, они пропускаются - вслух, но пропускаются; чтобы в CI это было провалом, а не зелёной галочкой при невыполненной проверке, там выставлена переменная `MEMCHECK_REQUIRE_SH=1`. Мутационная проверка выставляет её сама: без неё пропущенные тесты хука выглядели бы как «мутацию никто не поймал». И ещё: хук предназначен для запуска (`sh .githooks/pre-commit`), а не для подключения через точку. Если его подключить в свой скрипт как `. .githooks/pre-commit`, его `exit` оборвёт всю вашу цепочку хуков.

Они же гоняются на pull request и на push в `main` - на Ubuntu и на Windows. В обычных ветках идёт разработка, там возможно любое состояние, и красная галочка на них ничего не значит. Обе системы здесь не для галочки: половина ловушек в проверке про расхождение между ними (регистр имён, связанные каталоги, окончания строк), и на одной системе такие дефекты просто не видны.

**Если копируете хук к себе:**

- сделайте его исполняемым: `chmod +x .githooks/pre-commit`, а на Windows - `git add .githooks/pre-commit && git update-index --chmod=+x .githooks/pre-commit`, потому что при `core.fileMode=false` (умолчание Windows) `chmod` не меняет режим, который уходит в git, а `update-index` работает только с уже добавленным файлом. Неисполняемый хук git пропускает **молча**, без единого сообщения, и вы будете уверены, что защищены;
- если в вашем репозитории нет `.gitattributes` с нормализацией окончаний строк - добавьте туда `.githooks/** text eol=lf`. Иначе файл, закоммиченный с Windows, приедет с `CRLF`, и на Linux или macOS - в том числе у коллеги и в CI - `sh` откажется его запускать с невнятной ошибкой про интерпретатор. В самом Git Bash такой файл работает, поэтому автор проблемы её не увидит.

## Как это использовать

**Быстрый путь:** дайте своему агенту промпт [`prompts/setup-memory.md`](./prompts/setup-memory.md) - он развернёт саму память. Проверку согласованности он не ставит, её подключают отдельно (см. [«Проверка согласованности»](#проверка-согласованности)).

**Вручную** (те же шаги, что делает промпт):

1. **Отключить встроенную авто-память Claude Code** - в `.claude/settings.json` проекта:
   ```json
   { "autoMemoryEnabled": false }
   ```
   Иначе просьбы «запомни X» уходят в системную папку `~/.claude/...` мимо вашего `./memory/` (см. [«Про нативную память»](#про-нативную-память-claude-code)).
2. Скопировать папку [`memory/`](./memory) в свой проект. Нужна проверка согласованности - копируйте и [`scripts/`](./scripts) с [`.githooks/`](./.githooks), одной `memory/` для неё мало. Работает при этом **один файл** - `scripts/check_memory_index.py`; остальное в `scripts/` это тесты и наш внутренний инструмент мутационной проверки, они нужны, только если вы собираетесь проверку править. Сразу после копирования сделайте хук исполняемым и добавьте `.gitattributes` - см. [чеклист «Если копируете хук к себе»](#тесты-и-ci); обе ловушки срабатывают на первом же `git add`.
3. Вставить блок из [`CLAUDE.example.md`](./CLAUDE.example.md) в свой `CLAUDE.md`, **включая строку импорта** `@memory/MEMORY.md` - именно она делает индекс всегда загруженным. Путь импорта считается относительно файла: из корневого `CLAUDE.md` это `@memory/MEMORY.md`, из `./.claude/CLAUDE.md` - `@../memory/MEMORY.md`.
4. Почистить примеры под себя и начать с 3-4 реальных фактов в индексе.
5. Проверить: в новой сессии спросить «что ты знаешь из памяти?» (агент пересказывает индекс, не открывая файлы) и «запомни: <факт>» (в `memory/` появляется новый файл + строка в `MEMORY.md`, а не в системной папке).

Импорт кладёт **содержимое** индекса в контекст каждую сессию. Прозаическое «прочитай MEMORY.md» тоже загрузится как текст, но выполнение чтения агент решает сам - импорт надёжнее. Для жёстких гарантий (заставить дописывать память) нужны уже hooks, а не инструкция-контекст.

> **Переносимость.** Основной таргет - Claude Code (авто-загрузка `CLAUDE.md` / `.claude/CLAUDE.md` + импорты). Cursor и Windsurf подхватывают `AGENTS.md` схоже, но все агенты трактуют инструкции как контекст, не как принудительную конфигурацию, и детали авто-загрузки различаются - под конкретный агент адаптируйте.

> **`.claude/` и git.** Если ваш `.claude/` исключён из git (частый случай), строка импорта и `settings.json` в нём не поедут в репозиторий: память работает локально, но на свежем клоне не подхватится. Для «clone-and-go» держите импорт в отслеживаемом файле - корневом `CLAUDE.md`.

## Про нативную память Claude Code

У Claude Code есть **своя** авто-память того же вида (индекс `MEMORY.md` + topic-файлы с frontmatter), включённая по умолчанию. Отличие в том, **где** она живёт: в системной папке пользователя `~/.claude/projects/<проект>/memory/` - вне репозитория, привязана к машине и не едет с проектом. Просьбы «запомни X» по умолчанию попадают туда.

Мы держим память **в проекте под git**. Поэтому нативную авто-память выключаем (`autoMemoryEnabled: false`), а протокол в `CLAUDE.md` забирает «запомни» на себя и пишет в `./memory/`. Перенаправить нативную память в проект нельзя надёжно: её путь (`autoMemoryDirectory`) не принимает относительных путей.

Что это даёт: память лежит под git - история, diff, откат, ревью в PR; едет с репозиторием и доступна всей команде, а не одному пользователю на одной машине; это обычные md-файлы, которые читает и правит кто угодно.

Цена - разовая настройка и выключенная авто-память. Нативная выигрывает в «ноль усилий»: включена сразу и сама ловит «запомни». Выбор - контроль и портируемость против авто-магии из коробки. Если проектная портируемая память вам не нужна (личный проект на одной машине) - нативной достаточно, этот репозиторий не обязателен.

**Перенос из нативной памяти.** Если проект уже пользовался нативной авто-памятью, промпт [`setup-memory.md`](./prompts/setup-memory.md) найдёт её, спросит, перенести ли записи в `./memory/` (все или выборочно), перенесёт выбранное в наш формат и заархивирует native-папку переименованием (`memory` → `memory.bak`), не удаляя. Вручную - то же: скопируйте нужное из `~/.claude/projects/<проект>/memory/` в `./memory/`, затем переименуйте native-папку в `memory.bak`.

---

## Как откатить

Всё обратимо, ничего не удаляется безвозвратно:

1. **Вернуть нативную авто-память** - в `.claude/settings.json` поставить `"autoMemoryEnabled": true` (или убрать ключ / тумблер в `/memory`). Если архивировали native-папку - переименуйте `memory.bak` обратно в `memory`, и прежние записи снова активны.
2. **Выключить нашу** - убрать из `CLAUDE.md` строку импорта `@memory/MEMORY.md` и раздел `## Память`. Папку `./memory/` можно оставить (просто не подключена) или удалить.

Выключение нативной памяти её файлы не удаляло, а наши изменения - это строки в `CLAUDE.md` и папка в проекте под git.

## FAQ

**Оно сохраняет всё подряд, что я пишу?**
Нет, выборочно. Память пишется по явному «запомни» ЛИБО когда агент узнаёт долгоживущий факт (предпочтение / ограничение проекта / исправление). Обычная беседа, разовые указания и то, что уже есть в коде или git - не сохраняются, иначе индекс распухнет и перестанет быть сигналом.


**Не раздуется ли контекст, когда фактов станет много?**
Нет. На старте грузится только индекс `MEMORY.md`; topic-файлы читаются по требованию. Разросшийся индекс дробится на под-индексы. (Нативная память устроена так же, с потолком индекса ~200 строк / 25 КБ; наш импорт грузит индекс целиком - держите его тонким.)
